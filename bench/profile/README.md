# Профиль на n = 1e6: где время и что даст C++

Ядро не менялось (замороженное состояние после 7f79356; коммиты ui его не трогают). Данные:
`gen --n 1000000 --versions 1 --seed 1` (v1, 209 МБ), v2 = `bench.mutate(v1, 10 000)`
(d = 1%, семь видов изменений по кругу, как в `flat_vs_tree`). Хранилище: v1 закоммичен с
65 536 бакетами, профилируется commit v2 поверх него. Apple M4 Pro, 24 ГБ, APFS, Python 3.13.9.
Время — минимум из 3 прогонов после прогрева.

## Как мерили

- **Итог**: настоящие `diff(read_jsonl(v1), read_jsonl(v2))` и `Store(repo).commit(read_jsonl(v2), …)`,
  с включённым и с выключенным сборщиком мусора (`gc.disable()`).
- **Стадии** (`profile_stages.py`): те же вызовы ядра с таймерами между ними. `Rec.of`,
  `Store.commit` и `Store.put` повторены в скрипте с таймерами внутри. Проверено, что поэтапный
  flat даёт тот же отчёт, что `diff()`, а поэтапный commit — то же имя коммита, что `Store.commit`.
  Стадии мерились с выключенным gc, а время gc посчитано как разница итогов: с ним и без него.
  С включённым gc поэтапный прогон ненадёжен: flat при другом порядке выделения памяти занимал
  62 с вместо 39 (`stages_flat.json`).
- **Части `Rec.of`**: каждая операция отдельным проходом по тем же 2 млн записей.
- **Сортировки** (`sort_share.py`): `sorted()` из `validate` и `match` отдельно, на тех же данных.
- **cProfile** (`flat.prof`, `commit.prof`, `*_top.txt`): для проверки атрибуции. Под профайлером
  flat идёт 55,6 с, commit — 35,7 с, поэтому доли в таблицах взяты из замеров без профайлера.
- Файловая система: прогрев кеша страниц, без `fsync`, как в ядре. Новые объекты между прогонами
  удаляются, HEAD возвращается назад.

## Что ускорит C++

Оценка по пропускной способности, не по замеру: simdjson — около 1–2 ГБ/с, blake2b на M4 —
около 1 ГБ/с, `std::sort` и хеш-таблицы — в 10–20 раз быстрее словарей Python, сборщика мусора нет.

| стадия | flat сейчас → C++, с | commit сейчас → C++, с | почему |
|---|---|---|---|
| сборщик мусора | 16,3 → 0 | 6,7 → 0 | в C++ его нет (но см. ниже про `gc.disable`) |
| `json.loads` | 2,0 → 0,2–0,4 | 1,0 → 0,1–0,2 | simdjson |
| `json.dumps` | 5,9 → 0,4–0,8 | 4,5 → 0,3–0,5 | свой сериализатор |
| normalize | 1,2 → 0,1–0,2 | 0,6 → 0,05–0,1 | NFC через utf8proc или ICU |
| blake2b | 1,1 → 0,5–0,8 | 1,2 → 0,35–0,6 | упирается в объём данных, а не в Python |
| validate, сортировки, match | 9,4 → 0,6–1,0 | 4,1 → 0,3–0,45 | хеш-таблицы, `std::sort` |
| утечки, digest, обвязка, освобождение памяти | 3,1 → 0,1–0,2 | 1,6 → 0,1–0,15 | |
| **не ускорится**: ФС | 0,2 (чтение) | 3,8 + 0,1 | системные вызовы APFS — та же цена |
| **не ускорится**: zlib | — | 0,92 | та же libz (libdeflate дал бы ~×2: другие байты, но тот же формат) |
| **не ускорится**: sha256 | — | 0,13 | и так OpenSSL |
| **итого** | **39,2 → 2,1–3,6** | **24,6 → 6,2–7,0** | |
| **ускорение** | **≈ ×11–19** (от варианта без gc 22,9 с: ×6–11) | **≈ ×3,5–4** (от 18,0 с: ×2,6–2,9) | |

У commit нижняя граница — ФС + zlib + sha256 ≈ 4,9 с, то есть 70–80% времени будущей версии на C++.
Чтобы опуститься ниже, нужен другой формат хранилища (pack-файлы вместо файла на объект) или
параллельная запись. Оба способа доступны и из Python: на системных вызовах GIL отпускается.

## Оговорки

- **Совместимость байтов.** `raw_hash`, `payload_hash`, digest в заголовке патча и имена объектов
  зависят от точного вывода Python `json.dumps(ensure_ascii=False[, sort_keys=True])`. C++ должен
  повторить его байт в байт: разделители `", "`/`": "`, `repr` у float (`1e-05`, `Infinity`, `NaN`),
  экранирование управляющих символов, порядок ключей как при разборе, включая повторы. Кроме
  того, нужны та же версия Unicode для NFC (у Python 3.13 это 15.1) и полный Unicode-`lower()`
  (`'İ'.lower()` даёт два символа). Иначе старые хранилища и патчи станут несовместимы.
- **Сборщик мусора** — самая крупная статья, и она нестабильна: 16–39 с в зависимости от порядка
  выделения памяти. Ту же долю убирает `gc.disable()`/`gc.freeze()` на время `diff`/`commit`
  (циклов в данных нет): flat 39,2 → 22,9 с (×1,7), commit 24,6 → 18,0 с (×1,37). Это изменение
  ядра, поэтому сейчас не сделано.
- Задвоенная сериализация в commit (`line_hash` и тело бакета дважды строят одну и ту же
  `json.dumps(rec)`, 1,5 с) — тоже питоновская правка, C++ для неё не нужен.

## Файлы

- `profile_stages.py` — подготовка данных, поэтапные замеры, cProfile.
- `sort_share.py` — сортировки внутри `validate` и `match`.
- `stages_flat_nogc.json`, `stages_commit_nogc.json` — стадии без gc (основа таблиц).
  `stages_flat.json`, `stages_commit.json` — с gc, там же 3 прогона настоящего `diff()`.
- `flat.prof`, `commit.prof` — для `python -m pstats` или snakeviz. `*_top.txt` — топ по tottime и
  cumtime, `*_categories.json` — tottime по категориям.
- `run.log`, `run2.log` — вывод прогонов.

Повторить (~25 мин, ~1 ГБ на диске):

```sh
W=/tmp/dsdiff-prof
python bench/profile/profile_stages.py prepare --work $W
python bench/profile/profile_stages.py flat --work $W; python bench/profile/profile_stages.py flat --work $W --no-gc
python bench/profile/profile_stages.py commit --work $W; python bench/profile/profile_stages.py commit --work $W --no-gc
python bench/profile/profile_stages.py cprofile --work $W
python bench/profile/sort_share.py $W
```
